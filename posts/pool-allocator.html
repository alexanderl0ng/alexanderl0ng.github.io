Pool Allocators

2026-11-25

Introduction

While building a limit order book I wanted a faster way to allocate an Order instead of using the standard heap allocation. A useful property of this problem is that every allocation will be of a constant type and size. A potential solution is something I have previously implemented: an arena allocator. This would allow fast allocations, but it had no freelist. As a result, it could not free individual allocations. Therefore, a fast allocator that could free individual allocations was needed. Enter the pool allocator.

Implementation

The pool allocator, similar to an arena, reserves a large block of memory upfront, splits it into slots, and then maintains a list of free slots. There are many ways to implement this, such as an index-based freelist. I chose to use an intrusive freelist. This means the slot itself stores the address of the next free slot, and the pool only stores a pointer to the first free slot. A pool for a small type, less than 8 bytes, would likely use less memory in an index-based freelist. The intrusive freelist provides O(1) allocations and deallocations. However, as the program runs, the freelist order drifts from the address order. Therefore, consecutive allocations land on unrelated cache lines, increasing the chance of a cache miss.

There are three main functions: create(), allocate(), and destroy(). destroy() can be used for objects allocated via either create()/allocate(). If the object is not trivially destructible then destroy() will call the destructor. The difference between create() and allocate() is small. If an object is trivially constructible and trivially destructible, either can be used. Otherwise, create() must be used. Both will construct the object with placement new, but only create() has a SlotGuard, which will return the slot if the constructor throws. When the pool is full, create() or allocate() will return nullptr. The pool never grows.

The implementation has some debug-only helpers. There are two private data members: live_count_ and live_flags_. live_count_ exists in every build because it backs size(), but it is only checked in debug builds. The idea behind both of these is to track if any slots are not freed when the pool is destroyed. live_count_ can be used initially to determine if any slots are still allocated. live_flags_ also validates that there are no double frees during destroy(). destroy() also holds checks that a pointer being destroyed must lie within the pool, which catches foreign pointers in debug builds.

Lastly, the entire pool lives inline as a fixed-size array and never allocates. The capacity is a compile-time template parameter. Small pools can live on the stack, but larger pools should be placed on the heap using make_unique. The pool is not thread-safe, and it cannot be copied or moved.

These benchmarks were generated on an AMD Ryzen 7 9800X3D under Arch Linux, built with g++ -std=c++23 -O2 -DNDEBUG. See benchmarks/bench.cpp for details.

The workload for each benchmark is about 100,000 creates and deletes of a 64-byte cache-line-aligned Order. The argument (/1000, /10000, /100000) is the number of Orders resting in the pool. The time/op is the mean time per create or delete. The Baseline benchmark is the same loop but without any allocations, so it measures the overhead of the benchmark. Subtract this value from the other rows to get the cost of the allocator alone.

After subtracting the baseline, the pool is roughly 7x to 9x faster than new/delete: about 0.6-1.0 ns per operation against 5.0-6.6 ns. Measured end to end, the whole loop is roughly 2.3x to 2.5x faster.
